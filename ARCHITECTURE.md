# AsterLauncher architecture

## Beta 0.1.1 distribution

`Directory.Build.props` is the version source. The app displays its informational version, and the project builds a single-file, self-contained x64 release named `AsterLauncher.exe`. `eng/package-release.ps1` creates a full ZIP and `aster-update.json`; later versions may also include a fixed-block binary delta from one exact previous version. The Settings page lists GitHub Releases rather than using the latest-release endpoint, so beta prereleases are visible. It selects an exact-base delta when supplied and a full ZIP otherwise, verifies both the downloaded archive and replacement EXE with SHA-256, then stages the replacement outside the running executable and restarts. User `Data` is outside the release ZIP. The remote update path requires an uploaded Release and remains unverified until one exists.

The public source and ZIP include 26 attributed publisher-media files plus one original SVG fallback after the project owner confirmed redistribution authorization for this release on 2026-09-24. Publisher images remain publisher-owned and are not relicensed by any source-code license. Game identity, theme gradients, and user-selected local artwork remain available as fallbacks. The Endfield installation used for local validation is Bilibili B-channel; the 0.1.2 release adapter did not persist or infer a channel from `Endfield.exe`.

AsterLauncher is an original WinUI 3 application. It does not reuse Starward source, assets, layouts, or branding.

## Boundaries

- `AsterLauncher.Core`: framework-neutral domain models, adapter contracts, scan results, launch orchestration, argument parsing, and extension points such as `IGachaProvider`.
- `AsterLauncher.Infrastructure`: JSON persistence, evidence-based install locators, process detection, owned-process lifetime management, logging, built-in adapter implementations, and UIGF v4.2 archive/capture services.
- `AsterLauncher.App`: WinUI 3 views, view models, dependency injection composition, file pickers, and navigation.
- `AsterLauncher.Tray`: a small Windows Forms notification icon host; the WinUI window owns the close policy and restore action.
- `AsterLauncher.Core.Tests`: deterministic tests of launch order, failure policies, replacement launchers, owned-process cleanup, and evidence-based Endfield lookup.

The main UI consumes `IGameAdapter` instances and never branches on a concrete game ID for launching or discovery. Game-specific behavior stays inside an adapter. `BuiltInGameCatalog` registers Endfield, Genshin Impact, Honkai Impact 3rd, Honkai: Star Rail, Zenless Zone Zero, Petit Planet, and Arknights at compile time. Dynamic DLL loading remains deferred.

The game library persists an ordered list of game IDs and an explicit list of hidden built-in IDs in the existing JSON configuration. Older configurations default to showing every built-in game. Hiding a built-in keeps its executable path, history and launch profiles; restoring it moves it to the end of the visible rail. Custom game removal deletes that custom configuration and its profiles after confirmation, without touching the executable. Both visible and hidden lists can be reordered. Adding an EXE first matches the catalog's known executable names case-insensitively and then uses the matched adapter's manual validation; a successful match restores that built-in identity instead of creating a duplicate custom game. Games without a verified executable name remain manual/custom until the catalog has evidence for a name.

Game Library drag reordering updates the same ordered ID list after a completed drag. Its bulk cleanup acts only on visible games whose saved executable does not exist: built-ins move to the hidden library, while custom game configuration and profiles are removed after a count-specific confirmation. No game files or local record archives are deleted. The Win32 window subclass enforces a 960×540 DIP minimum client area at the current window DPI, alongside the existing 16:9 interactive resize rule.

## Launch pipeline

`BeforeGame -> Game -> AfterGame -> wait for game exit -> OnGameExit -> close owned companions`

Every external process is started from a file path with a structured argument list. The service records the exact `Process` instance it created. Cleanup can only target those owned handles; a pre-existing process may be detected and skipped, but is never acquired or terminated.

An adapter supplies its definition, install locator, process detector, default launch arguments, and optional feature declarations. An explicit takeover step suppresses the default game executable and lets a user-selected tool launch the game.

## Data and privacy

MVP settings are JSON because the data is small and document-shaped. Passwords and account credentials are out of scope. The data root is selected by an EXE-adjacent `asterlauncher.data-location.json`, then `ASTERLAUNCHER_DATA_HOME` for development, then an EXE-adjacent `Data` directory. `Environment.ProcessPath` locates the installed EXE; `AppContext.BaseDirectory` can be the single-file extraction directory and is used only for packaged read-only assets. The first 0.1.1 launch copies the newest beta 0.1.0 bundle-extraction data to the EXE-adjacent Data directory when that directory is empty; it leaves the legacy copy intact. Settings can copy data to an existing empty directory and restart. Build/run scripts set the development override to project-local `.appdata` on E:. The .NET single-file runtime may still unpack native files into its own temporary directory; app-owned configuration, logs, records and artwork do not use that directory.

Automatic discovery reports each checked source and a typed outcome. Endfield discovery is deliberately narrow: saved executable path first, then the executable path of a running `Endfield.exe`, then standard uninstall entries whose display name is exactly `鹰角启动器` or `GRYPHLINK`. A locally inspected installation established the relative path `games\Endfield Game\Endfield.exe`; no disk-wide scan, random uninstall key, or unverified vendor configuration format is used. Manual selection always remains available and overrides an automatic result.

The first-run guide saves a user-selected game directory. A later scan checks the existing adapter locator first, then searches only that directory and its subdirectories for the executable names declared by each built-in adapter. It skips directory links, caps directory traversal, and asks for manual selection when multiple installations match. For the miHoYo games, the existing locator checks a saved path; the selected-directory search adds `YuanShen.exe` / `GenshinImpact.exe`, `BH3.exe`, `StarRail.exe`, and `ZenlessZoneZero.exe`. Petit Planet has no verified executable name, so it remains manual-only. No unverified HoYoPlay registry or configuration rule is assumed.

## Downloads and companion tools

Built-in definitions expose an official download/documentation URI, not an embedded package downloader. HoYoPlay's modern Sophon flow and publisher launchers require live manifests, integrity checks, patch state, and channel handling; v0.4 intentionally opens the publisher source instead of copying an incomplete URL algorithm. Arknights and Endfield link to the official Hypergryph PC flow. `CompanionToolPresetFactory` supplies user-path-only templates for MAA/maa-cli, MaaEnd, March7thAssistant, and BetterGI; it downloads nothing and preserves the owned-process safety boundary.

The game directory preference is persisted as the target for a future in-app downloader and is used for bounded discovery now. The current official-link action cannot control the publisher installer's destination; the guide and settings page state this explicitly. The X button preference is persisted as exit or minimize to tray; tray restore and exit use the Windows Shell notification area.

`WallpaperUpdateService` reads publisher metadata once after startup for the five HoYoPlay CN games, Endfield, and Arknights. It only downloads an image if the publisher URL changed or its validated local JPEG cache is missing. The cache and URL hash index live under the configured `Data/artwork/cloud` directory; no account credentials are sent. A failed metadata or image request preserves the existing cache and packaged fallback. Artwork precedence is explicit user selection, user data artwork, verified cloud cache, then packaged art or adapter gradient. During a running launcher session, `GameCardViewModel` reuses a `BitmapImage` for each unchanged file (path, modification time, length), and `MainWindow` keeps decoded wallpaper layers for return visits. No game switch makes a network request. The sidebar icons, Endfield pool banners, and cataloged Star Rail/Endfield character portraits remain bundled. The portrait manifest records an exact official CDN source for every bundled portrait; missing names fall back to glyphs.

The profile editor projects the existing ordered `LaunchStep` list into an observable sequence that includes the default game executable when no takeover step is enabled. This projection mirrors the orchestrator's four phases and updates immediately after add/remove/select actions. Profile creation, rename, and deletion persist through the existing JSON store; the launcher keeps at least one profile per game. The settings UI groups app information, appearance, and window/path options into tabs. Theme presets only mutate original AsterLauncher color brushes; they do not contain third-party images.

## Gacha boundary

`IUigfArchiveService` is independent of `GameLaunchOrchestrator`. It imports and exports UIGF v4.x JSON and stores a project-local v4.2 archive. Capture is limited to verified HoYo Web cache layouts and official history endpoints for Genshin Impact, Honkai: Star Rail, and Zenless Zone Zero. The temporary history URL and `authkey` are never persisted or logged. Requests are paced and ordinary pools retry a temporary `-110` response. The Star Rail 21/22 categories may return `-110` while other categories succeed; those two are reported as unavailable without discarding successfully fetched records. Arknights and Endfield remain outside this provider because they do not use UIGF.

Endfield has its own local JSON archive service. A rejected character/weapon record group no longer discards valid groups; the result explicitly reports partial sync. The restricted parser accepts a `data.list`, `data.records`, or array `data` envelope, and logs only a locally constructed, token-free error category or numeric server code. Stored and exported records are scrubbed of authorization fields and official record URLs. The cache may contain URLs from several sessions, so the reader applies the newest token for each official host and server to all discovered pools. The first request omits `seq_id`; later pages use the last record's `seqId` as the cursor. Normal sync stops when a page reaches a record already present in the local archive, keyed by pool and sequence; a separate full-sync action scans every page to fill historical gaps. On 2026-09-24 a controlled official request and the isolated WinUI sync both succeeded: the archive contained 420 character records and no weapon records. The archive was checked for token and authorization URL fields.

Star Rail analysis is a read-only projection of the local UIGF hkrpg array. It separates accounts by UID and record categories by gacha_type; records are ordered by local record time and numeric-string ID. The dense category sections show every recorded five-star as a visible progress row; an optional detail expander groups records by exact gacha_id. Five-star intervals and current local waterlines run across IDs within that category. Character activity (11), light-cone activity (12), standard (1), and departure (2) remain independent; 21/22 are shown as unverified special categories without a guessed guarantee. At sufficient width the character history uses two compact row columns, while other categories stack beside it; narrower views use full-width sections. Banner-ID detail is secondary and never resets the category counter. A local record cannot prove that a banner is still active. UIGF does not carry a display name or featured-item roster for each gacha_id, so the UI withholds UP win/loss and next-featured status until a verified catalog exists. The first observed five-star interval is labeled as a local lower bound. No derived statistic or authorization URL is persisted.
Endfield analysis reads the existing local archive on demand and does not persist derived statistics. It counts character `draw` records, excludes non-draw rewards, sorts by record time and sequence, and groups normal pools by exact pool ID. Re-Factor analysis uses the recorded `poolVersion` as a phase key, falling back to the recorded title if the version is missing, so a later same-name phase cannot merge its totals and six-star list into an earlier one. The display groups these distinct phases into one named-series card: its highest numbered phase is shown by default and older phases open inside that card. Archive merge and incremental checkpoints include the phase version in their identity. Each card exposes its phase total, paid and free draws, free six-stars, and six-star occurrence positions. A free draw neither advances nor resets paid pity. A source-reviewed catalog identifies announced Chartered pools since launch, the `绚丽异彩` Re-Factor series, and the separate `辉光庆典` event; future `rerun_chr_` pools use generic Re-Factor rules and a fallback texture until their featured operator is verified. The 80-draw Re-Factor six-star pity is shared across all Re-Factor series and phases. The first-120 paid-draw UP observation is shared only across phases of the same named Re-Factor series and can trigger once. Official 30/60/90 free ten rewards and each 240-draw featured token also follow same-name accumulation, but this UI does not yet project reward eligibility. Standard and Chartered pity remain separate. Expanded six-star bars use the shared family count, and the top strip shows a shared 80 progress bar and a same-name first-120 UP indicator. Series cards with history occupy the available content width; other cards use one or two columns according to space and count. A count above 65 shows dark red. These are estimates from the local archive, which can be incomplete, not verified live game pity. The character rules follow the publisher's [Re-Factor announcement](https://endfield.hypergryph.com/news/4776) and [绚丽异彩 notice](https://endfield.hypergryph.com/news/2651); weapon Re-Factor rules are distinct and not projected into the character analysis.

## Endfield channel maintenance under development

The development tree retains the original single game page and GameLaunchOrchestrator. Configuration schema 4 adds an explicit selected Endfield channel and separate installation records. A legacy executable path stays unclassified until the user selects a channel; merely finding Endfield.exe never identifies official versus Bilibili. The launch button and its existing expansion consume EndfieldMaintenanceViewModel. The selected channel is observable in the sidebar badge, path, version, primary command, progress and maintenance panel. Every page entry makes a lightweight version check; asynchronous responses update their originating channel state.

EndfieldDistributionProvider makes the public publisher request for channel/sub-channel 1/1 or 2/2. It asks for full pkg metadata independently from a versioned patch check, verifies encrypted game_files MD5 before AES-CBC decoding, and rejects empty, duplicate or unsafe manifest paths. Signed resource URLs stay in memory. EndfieldDownloadService keys its E-drive cache by expected MD5 and length and handles partial HTTP responses. EndfieldMaintenanceService serializes work by physical install root, guards running game processes, checks the complete selected-channel manifest, downloads defective files with bounded concurrency, commits via VerifiedFileCommit, and only then records the installed version. The safe commit writes a verified same-volume temporary file and replaces one channel directory entry, so AsterLauncher never writes through a shared hard link.

EndfieldSharingService is independent of the publisher protocol. It only links matching hex-named VFS .chk files from the observed local directory structure, after comparing both manifests and hashing the source. It holds the source file open without write sharing during link creation, then verifies NTFS file identity and hash. It excludes executables, config.ini, account files, indexes and other potentially mutable files. A local identity scan reports existing sharing without trusting a saved database; estimated saved bytes use GetCompressedFileSizeW for each verified shared file, while shared content bytes remain a separate count. The unshare operation copies each linked current-channel file through the same safe commit path. Cross-volume or non-NTFS candidates remain independent. The launcher cannot prevent an external game/official updater from writing a linked resource in place; users should unshare before such maintenance.

This implementation has not completed multi-volume ZIP extraction, formal patch.json/VFS/HDiff application, predownload-to-update reuse, seamless multi-file application OTA from the released 0.1.2 updater, or real full-install/game-launch acceptance. The existing 0.1.2 distribution and updater are single-file. Do not present this development tree as a released 0.1.3-beta package.

## Multi-file migration utility (development)

`AsterLauncher.Migrator` is an independent, self-contained .NET executable distributed with the multi-file package. `eng/create-migration-package.ps1` places a patched .NET apphost at the package root as `AsterLauncher.exe`, with the WinUI publish beneath `App/` and the migrator runtime beneath `MigrationTools/`. The root has one EXE and a small number of directories. The apphost starts `MigrationTools/AsterLauncher.Migrator.dll`, which launches `App/AsterLauncher.exe`. No user data enters the release ZIP.

The `--migrate` command requires an external SHA-256 for the entire ZIP, validates every ZIP path and per-file SHA-256 in `release-files.json`, extracts to a same-volume staging directory, and then swaps the entry and application directories. The old entry and any old `App` or `MigrationTools` directories go under `MigrationBackup`; a journal records the transaction. `--recover` uses that journal to restore the old entry after an interrupted switch. It refuses unexpected links and a modified root entry. The new app recognizes the parent installation directory, so `Data` and `asterlauncher.data-location.json` remain outside `App` even after a later Settings relocation. This utility neither reads nor edits game installations or account credentials.

An E-drive fixture used the actual 0.1.2 ZIP as the old entry and a current multi-file development publish as the target. SHA and internal-file corruption were rejected before swap; the old EXE's hash survived in the backup; the patched entry launched the nested WinUI app with the existing custom data pointer. The 0.1.2 updater still accepts only a one-EXE ZIP and cannot invoke this migration utility directly. A published 0.1.3 OTA handoff and later multi-file delta updater remain separate release gates; the current development ZIP is not a 0.1.3 release.
## 0.1.3-beta 渠道维护与多文件交付

EndfieldDistribution.cs 定义渠道、安装实例、资源清单、预下载与阶段状态。渠道独立保存目录、版本、任务、预下载身份和所选启动方案；旧 GameId 配置/抽卡档案继续保留。可信安装识别同时核对官方 appcode、channel/sub_channel、版本、入口与实际 MD5，不用 EXE 名称猜渠道。

EndfieldDistributionProvider 始终从实时官方 API 分开获取更新结果与完整清单，先校验清单密文 MD5 再解码。EndfieldNodeHttpHandler 通过单独的便携 OpenSSL HTTPS 进程解决本机 Schannel 认证失败，只允许发行商公开分发主机；URL 经 stdin 输入，响应流直接进入下载器，不保存授权/签名地址。下载缓存采用 MD5+长度内容身份，URL 刷新不会改变已验证缓存键。

EndfieldMaintenanceService 对物理根目录加进程内和磁盘锁。完整安装/更新按官方逐文件清单同步，安装第二服先匹配并验证可共享资源，再计算剩余下载。`.aster-maintenance.json` 记录安装 ID、渠道、源/目标版本与清单哈希，不保存 URL；中断后重新取得官方目标并校验已经提交的内容。目标变化、校验失败或取消不会提前发布成功版本。config.ini 单独在资源复验后提交；维护提交前再次检查两服游戏是否运行。

VerifiedFileCommit 一律在目标同卷生成独立临时文件、哈希复验、刷新落盘，再替换当前目录项，实际已有多少硬链接都不影响另一服内容。EndfieldSharingService 独立于渠道协议，只允许明确的 VFS .chk 候选，验证双清单、实际内容和 NTFS 文件身份；源句柄在共享转换期间禁止写入。解除共享扫描真实链接数，不依赖索引，也处理异常共享的配置文件。外部进程的原地写入无法由此服务约束，真实游戏 .chk 不可变性仍需扩大实测。

预下载只进入内容缓存；正式 patch 重新取得后核对并复用。EndfieldArchiveService 用独立便携 7-Zip 列出并检查全部压缩路径，拒绝链接与越界，把每个目标文件流式输出到私有暂存区，再按官方目标清单校验；多卷从第一卷作为一个 ZIP 读取，支持 cd_key。HDiff/VFS 增量输出回退为目标文件同步，不原地写入源，也不冒充已验证的原生增量实现。

WinUI 通过 EndfieldMaintenanceViewModel 的渠道状态消费服务；主按钮承担下载/更新/进度/暂停，右侧展开区共用启动选项样式。异步回调更新原渠道状态字典，选中渠道变化不会转移任务或把响应写入另一渠道。GameLaunchOrchestrator 保持启动职责。

多文件发布根为入口、App、MigrationTools 与校验清单。LauncherDataPaths 在 App 内运行时回到安装根解析 Data/位置文件。0.1.2 单 EXE 需独立迁移器一次迁移；0.1.3 以后的 OTA 使用 format=2 清单，完整包和文件差量在安装卷暂存、逐文件复验，由暂存区中的独立迁移运行程序提交并保留备份。旧客户端清单名与新版分开，防止旧更新器接收不兼容包。版本标签触发 GitHub Actions 的隔离构建、测试、打包和 Release 附件 SHA-256 核对。
